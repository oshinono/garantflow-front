# ТЗ на разработку фронтенда (прототип v10.6.1)


## 1. Общие сведения

Нужно разработать production-фронтенд веб-приложения «Учёт заявок на банковские гарантии» (Garant Flow) как SPA на SolidJS + TypeScript, работающее с реальным бэкендом вместо localStorage.

**Источники требований.** Поведение, тексты и визуальный стиль берутся из интерактивного прототипа `prototype_v10_6_1.html` в корне репозитория. Контракт данных берётся из `api.md` и живой схемы бэкенда `/openapi.json`. При расхождении прототипа и API приоритет у API; такие места явно описаны в разделах 4 и 5.

**Как пользоваться прототипом.** Открыть файл в браузере и войти кнопкой демо-входа: там есть демо-воркспейс с 12 заявками во всех статусах. Код прототипа не переносится, он служит только эталоном UX. Ссылки в ТЗ вида «прототип: `renderToday()`» указывают на функцию в файле, где видно поведение.

**Что входит в работы:**

- все экраны прототипа: вход/регистрация/подтверждение почты, «Сегодня», доска заявок, карточка заявки (5 вкладок), лента, отчёты и сверка, банки, воркспейсы и участники;
- интеграция со всеми эндпоинтами из `api.md`, кроме `/metrics` и `/health` (последний — только для индикатора доступности);
- слой заглушек для функций прототипа, у которых пока нет API (реестр — раздел 8);
- экспорт в Excel, адаптивная вёрстка от 320 px, unit- и e2e-тесты, CI.

**Что не входит:** бэкенд, SSR, мобильные приложения, офлайн-режим, интернационализация (интерфейс только на русском), кредитные продукты.

**Терминология.** Заявка — запрос клиента (принципала) на БГ. Закупка — тендер или договор, под который нужна БГ. Запрос в банк (bank request) — работа с конкретным банком по заявке. Гарантия — факт выдачи. КВ — комиссионное вознаграждение агента. ОПЗ — дата окончания подачи заявок.

## 3. Архитектура и структура проекта

Приложение строится по фичам: каждый экран — отдельный модуль со своими запросами, компонентами и тестами; общий слой API ничего не знает о UI.

### 3.1 Структура каталогов

```text
/
├─ prototype_v10_6_1.html      # эталон UX, не импортируется
├─ api.md
├─ index.html
├─ vite.config.ts  tsconfig.json  eslint.config.js
├─ e2e/                         # Playwright
└─ src/
   ├─ app/          # корень, роутер, провайдеры (QueryClient, Auth, Toast), лейауты
   ├─ api/
   │  ├─ schema.d.ts            # сгенерировано из /openapi.json
   │  ├─ client.ts              # openapi-fetch + middleware (токены, X-Request-ID, ошибки)
   │  ├─ errors.ts              # ApiError, словарь code → текст
   │  ├─ queries/               # query keys и хуки по ресурсам
   │  └─ stubs/                 # заглушки недостающих эндпоинтов (раздел 4.5)
   ├─ domain/       # типы предметной области, маппинг API ↔ UI, расчёт КВ, проверка ИНН
   ├─ features/
   │  ├─ auth/  today/  board/  application/  feed/
   │  ├─ reports/  banks/  workspaces/  notifications/  templates/

   │  ├─ ui/                    # UI-кит (раздел 6)
   │  ├─ lib/                   # форматирование денег/дат, excel, hotkeys
   │  └─ hooks/

```

Открытая заявка и активная вкладка хранятся в URL, чтобы ссылкой можно было поделиться. Фильтры и поиск доски тоже синхронизируются с query-параметрами. Последний воркспейс и свёрнутость сайдбара хранятся в localStorage.

### 3.3 Состояние

- Серверные данные — только через TanStack Query; ключи вида `['ws', wsId, 'applications', filters]`. Мутации инвалидируют затронутые ключи.
- Сессия (токены, текущий пользователь) — `AuthContext` на сигналах Solid.
- Локальный UI (открытые поповеры, выделенные карточки, черновик формы) — сигналы и сторы внутри фичи, без глобального стора.
- Карточка заявки редактирует локальный черновик; сохранение отправляет PUT целиком, т.к. update в API — полная замена.
- Права считаются хелпером `can(action)` из роли пользователя в текущем воркспейсе и матрицы раздела 4 `api.md`; UI скрывает недоступные действия, но 403 с сервера всё равно обрабатывается.

## 4. Работа с API

Все запросы идут через один типизированный клиент на базе `openapi-fetch`; бизнес-маршруты — с префиксом `/api/v1`. Типы не пишутся руками: после изменения бэкенда запускается `yarn api:gen`, и `typecheck` ловит расхождения.

### 4.1 Клиент и обработка ошибок

- Middleware добавляет `Authorization: Bearer` и `X-Request-ID` (UUID на каждый запрос). `X-Request-ID` из ответа пишется в лог консоли и показывается в тосте ошибки 500 для передачи в поддержку.
- Ошибки приводятся к `ApiError { status, code, detail, requestId }`. Для каждого `code` из раздела 15 `api.md` есть русский текст в `errors.ts`; неизвестный код — показать `detail`.
- 422 без `code` (валидация FastAPI): разобрать `detail[].loc` и подсветить соответствующие поля формы.
- 409 конфликты показываются тостом с текстом из словаря, форма остаётся открытой с введёнными данными.
- 403 `permission_denied` — тост «Недостаточно прав» и обновление роли пользователя в кеше. 404 на ресурс воркспейса — экран «Не найдено» со ссылкой на доску.
- Сеть недоступна — тост с кнопкой «Повторить»; запросы TanStack Query повторяются 2 раза, мутации не повторяются автоматически.

### 4.2 Авторизация и токены

- Вход: `POST /auth/login` как `application/x-www-form-urlencoded` (`username` = email). При 429 показать таймер обратного отсчёта по `Retry-After` и заблокировать кнопку.
- 403 `email_not_verified` → экран `/check-email` с кнопкой `POST /auth/verify-email/resend` (после нажатия — кулдаун 60 с; ответ всегда 202, текст нейтральный).
- Access-токен хранится только в памяти. Refresh-токен — в `localStorage` (бэкенд отдаёт его в теле, cookie недоступны); это фиксируется как принятый риск, CSP в разделе 7 его снижает.
- Обновление: за 60 с до `expires_in` и при любом 401 — `POST /auth/refresh`. Запрос обновления один на всё приложение (single-flight), остальные запросы ждут его и повторяются один раз. Refresh одноразовый, поэтому вкладки синхронизируются через `BroadcastChannel`: новая пара токенов рассылается остальным вкладкам.
- 401 `invalid_refresh_token` → очистка сессии и переход на `/login?next=<текущий URL>`.
- Выход: `POST /auth/logout` с refresh и Bearer, затем очистка кеша Query и всех вкладок.
- Регистрация: `POST /users` (имя, email, пароль 8–128). Если открыта по ссылке-приглашению, передать `invitation_token`; тогда почта сразу подтверждена и можно логиниться.
- После входа: `GET /users/me` и `GET /workspaces`. Если воркспейсов нет — предложить создать первый (`POST /workspaces`), имя по умолчанию «<Имя> — воркспейс», как в прототипе.
- Приглашение `/invite?token=`: неавторизованного — на вход или регистрацию с сохранением токена, затем `POST /invitations/accept` и переход в полученный `workspace_id`. Ошибки `invitation_email_mismatch`, `invitation_expired`, `member_already_exists` — отдельные понятные экраны.

### 4.3 Деньги, даты, идентификаторы

- Суммы приходят и уходят строками-decimal, не более 2 знаков. Поля ввода денег принимают пробелы и запятую, отображаются с разделителями разрядов и «₽».
- `datetime` отправляется в ISO 8601 с часовым поясом пользователя. Дата ОПЗ вводится как дата и время (по умолчанию 23:59 по местному времени).
- ID — UUID. Номер заявки для людей: поле `number`, если заполнено, иначе короткий хвост UUID (`#a1b2c3`). Сквозная нумерация как в прототипе (№ 1, 2, 3) требует бэкенда — заглушка Z-07.

### 4.4 Как модель прототипа ложится на API

В прототипе заявка — один плоский объект. В API это четыре сущности: клиент, закупка, заявка и запросы в банки с гарантиями. Форма заявки остаётся единой, а сохранение раскладывается по сущностям.

| Поле прототипа | Сущность и поле API | Примечание |
| --- | --- | --- |
| Юрлицо / ИП, ИНН принципала | `client.name`, `client.inn`, `client.client_type` | Тип определяется по длине ИНН: 10 — `company`, 12 — `ip` |
| Принадлежность к ФЗ | `procurement.law_type` | «БГ по НДС» — не закон, а `guarantee_type = vat` без закупки |
| Реестровый номер, ссылка ЕИС, НМЦ | `procurement.registry_number`, `placement_url`, `nmc` | 44/223/615 |
| Дата ОПЗ | `procurement.application_deadline` | |
| Заказчик, ИНН заказчика | `procurement.customer_name`, `customer_inn` | Коммерческая |
| Номер и дата договора | `procurement.contract_number` + `contract_date` | Было одно текстовое поле, станет два |
| Вид БГ (участие, ОИК, ГО, аванс) | `application.guarantee_type` | `participation`, `oik`, `go`, `advance` |
| Бенефициар (ФНС) | `application.beneficiary_name`, `beneficiary_inn` | Для НДС обязателен, по умолчанию «ФНС» |
| Сумма БГ | `application.requested_amount` | |
| Срок действия БГ (текст) | `application.requested_valid_from` / `requested_valid_to` | Текст заменяется периодом дат; подсказка с числом дней |
| Ответственный | `application.responsible_user_id` | |
| Банк заведения | — | Нет в API, заглушка Z-08 |
| Статус по банку, комментарии | `bank_request.*` + заглушки | См. 5.4 |
| Данные о выдаче | `guarantee.*` | См. 5.4 |
| Клиент получил самостоятельно | `archive.client_obtained_independently` | Задаётся при архивации |

**Создание заявки** — последовательность запросов: найти клиента по ИНН (Z-01) или `POST /clients` → `POST /procurements` (кроме НДС) → `POST /applications`. Если шаг упал, уже созданные id сохраняются в черновике, а повтор продолжает с упавшего шага, не плодя дубли. Для НДС закупка не создаётся.

**Редактирование** — PUT каждой изменённой сущности целиком (полная замена). Перед PUT берутся актуальные данные из детального ответа, чтобы не стереть незаданные поля.

### 4.5 Слой заглушек

Для функций прототипа без API делается слой `src/api/stubs`. Требования:

- каждая заглушка имеет ту же сигнатуру, что будущий реальный хук, и предлагаемый контракт эндпоинта в JSDoc;
- данные хранятся в `localStorage` под ключом `stub:<wsId>:<ресурс>` — видны только в этом браузере;
- переключение на реальный API — замена одной функции, UI не меняется;
- при `VITE_USE_STUBS=false` функции-заглушки скрываются из UI с подсказкой «Скоро»;
- в MSW-обработчиках для тестов заглушки описаны так же, как реальные эндпоинты;
- каждая заглушка помечена комментарием `// STUB Z-xx` и перечислена в реестре раздела 8.

## 5. Экраны и функциональность

Каждый экран повторяет раскладку, тексты и состояния прототипа; ниже — что именно сделать, откуда брать данные и где поведение меняется из-за API. Коды Z-xx — заглушки из раздела 8.

### 5.1 Каркас приложения

- Левый сайдбар (прототип: `.sidebar`): логотип «БГ», переключатель текущего воркспейса, навигация «Сегодня, Доска (со счётчиком заявок), Лента, Отчёты, Банки, Воркспейсы», внизу аватар, имя, email и кнопка выхода.
- Сворачивание сайдбара до 76 px с иконками; состояние в localStorage. На ширине до 720 px сайдбар превращается в верхнюю панель с навигацией-чипами.
- Шапка страницы: надзаголовок, заголовок, описание и блок действий справа — тексты по экранам из `setPageMeta()` прототипа. Колокольчик уведомлений со счётчиком непрочитанных (Z-11).
- Тосты в правом нижнем углу, 3 с, с `aria-live=polite`.
- Горячие клавиши вне полей ввода и без открытых диалогов: `N`/`Т` — новая заявка, `/` — фокус в поиск доски, `Esc` — снять выделение карточек.

### 5.2 Вход, регистрация, подтверждение почты

- Двухколоночный экран: слева тёмный hero с текстом и тремя преимуществами, справа форма (прототип: `.auth-screen`, `showAuth()`). Кнопка демо-входа и «предпросмотр письма» из прототипа не переносятся.
- Формы входа и регистрации с валидацией: email 3–320, пароль 8–128, имя 1–255. Показ пароля, автозаполнение браузера.
- Экран «Проверьте почту» с адресом и повторной отправкой; экран результата подтверждения по ссылке (успех → вход, ошибка → повторная отправка).
- Сценарии и коды ошибок — раздел 4.2.

### 5.3 Сегодня

- Четыре KPI: «Мои заявки в работе», «Горят сроки (мои)», «Новые упоминания», «Без ответственного».
- Секции: мои горящие заявки (ОПЗ ≤ 3 дней или просрочена), упоминания (Z-11), горящие не мои, без ответственного (первые 8 и «и ещё N»). Строка открывает карточку заявки.
- Данные — список заявок воркспейса в статусе `in_progress` + дата ОПЗ закупки (нужна в списке, Z-02).

### 5.4 Карточка заявки

Модальное окно шириной до 960 px (на мобильных — полноэкранное) с вкладками «Данные о заявке», «Выдача», «Банки», «Вложения», «История». Заголовок «Заявка № …» или «Новая заявка», ссылка «Создана на основе заявки № …» для повторов.

**Данные о заявке.** Набор полей зависит от типа (прототип: `formR()`):

- общие: тип закупки (Коммерческая, 44-ФЗ, 223-ФЗ, 615-ПП, БГ по НДС), принципал, ИНН, сумма БГ, период действия БГ, ответственный, номер заявки, описание;
- 44/223/615: реестровый номер, ссылка ЕИС, НМЦ, дата и время ОПЗ, вид БГ;
- коммерческая: заказчик, ИНН заказчика, номер договора, дата договора, вид БГ;
- НДС: бенефициар (по умолчанию «ФНС») и его ИНН, без закупки и без выбора вида;
- банк заведения (Z-08) с предупреждением о превышении лимита банка (Z-05).
- Принципал выбирается комбобоксом с поиском по имени и ИНН среди клиентов (Z-01) или вводится новым. Архивного клиента выбрать нельзя.
- Проверки до сохранения: ИНН 10 или 12 цифр и контрольная сумма; возможный дубль (тот же ИНН и реестровый номер, либо тот же ИНН, тип и сумма); при предупреждениях — диалог «Сохранить всё равно?» вместо `confirm()`.
- Кнопки: «Повторить заявку» (новая форма с копией полей без выдач, банков и истории), «Сохранить как шаблон» (Z-14), «Отмена», «Создать заявку» / «Сохранить изменения». Несохранённые изменения при закрытии — диалог подтверждения.
- Архивная заявка открывается только для чтения с кнопкой «Вернуть в работу».

**Банки (обсуждения).** Список запросов в банки по заявке (`bank_requests[]`) вместо всех банков справочника, как было в прототипе. Кнопка «Добавить банк» выбирает активный банк и делает `POST /bank-requests`.

- По каждому банку: переключатель статуса «Рассматривает / Одобрено / Отказ» с повторным нажатием для сброса; поля `external_number`, `requested_amount`, `sent_at`, `decision_at`, `rejection_reason`, `notes`. Маппинг: «Рассматривает» — `sent_at` задан, `decision_at` пуст; «Одобрено» — `offer_received = true` и `decision_at`; «Отказ» — `offer_received = false`, `rejection_reason`, `decision_at`.
- Блок «Предложение банка»: ставка, комиссия, срок рассмотрения, условия (Z-04). Таблица «Сравнение предложений» подсвечивает лучшие значения; «Выбрать» ставит банк заведения и подставляет комиссию в форму выдачи.
- Лента комментариев по банку с автором, временем, редактированием и упоминаниями `@Имя` (кнопки-подсказки участников) — Z-03, Z-11.
- Удаление запроса — только OWNER/ADMIN, с подтверждением; 409 `bank_request_has_guarantee` объясняется текстом.

**Выдача.** Форма гарантии (прототип: `issuancePanel`): банк (из запросов заявки), номер БГ, дата выдачи, сумма, период действия, комиссия клиента банку, КВ %, сумма КВ, примечание, скан (Z-06).

- Переключатель «Что вводите вручную: Ставку, % / Сумму, ₽». Ставка → `agent_commission_is_manual = false`, сумма КВ показывается как `комиссия × ставка / 100` с меткой «авто» и не отправляется. Сумма → `is_manual = true`, ставка показывается расчётно (`сумма КВ / комиссия`).
- Если запроса в выбранный банк ещё нет, он создаётся автоматически перед `POST /guarantees`.
- Несколько гарантий («+ Ещё БГ по этой заявке») — только для аванса по коммерческой закупке; иначе кнопки нет. Ошибки `guarantee_limit_exceeded`, `guarantee_bank_already_used` — тексты из словаря.
- После первой выдачи заявка автоматически становится «Выданные»; кеш доски инвалидируется.

**Вложения** — загрузка нескольких файлов, список с размером, автором, датой, удаление (Z-06). **История** — `status_history[]` из API плюс журнал изменений полей «было → стало» (Z-09), новые сверху.

### 5.5 Доска заявок

- Три колонки по `ApplicationStatus`: «В работе», «Выданные», «Архив», с описанием, счётчиком и цветом колонки (цвета настраиваются, Z-13). Пользовательские этапы прототипа (`addStage()`) не делаются, пока их нет в API.
- Карточка: номер, тип закупки, клиент и ИНН, сумма БГ, банк заведения, номер закупки или договора, метка ОПЗ (красная «просрочена N дн.», жёлтая «сегодня / через N дн.» при ≤ 3 днях, только для «В работе»), чипы статусов банков, ответственный с быстрым выбором прямо на карточке.
- Перетаскивание между колонками плюс доступная с клавиатуры альтернатива — меню «Переместить в…». Переходы:
    - в «Архив» — диалог: причина и «Клиент получил БГ самостоятельно: да / нет / не указано» → `POST /archive`;
    - из «Архива» в «В работе» — диалог с комментарием → `POST /reopen`;
    - в «Выданные» — открывается карточка на вкладке «Выдача»; статус меняется только после сохранения гарантии;
    - из «Выданных» в «В работе» в API нет: drop запрещён, подсказка. 409 `invalid_status_transition` откатывает оптимистичное перемещение.
- Поиск по подстроке без учёта регистра: ИНН, клиент, заказчик, номер закупки и договора, номер заявки; комментарии и имена файлов — когда появятся Z-03 и Z-06. Фильтрация на клиенте по полному списку, т.к. пагинации нет.
- Панель фильтров в стиле Jira (прототип: `filterBar()`): мультивыбор «Банк», «Тип закупки», «Вид БГ», «Ответственный» (включая «Не назначен»), чипы «Мои заявки» и «ОПЗ ≤ 3 дней», «Сбросить фильтры», счётчик «N из M», наборы фильтров (Z-15), сортировка (по умолчанию, ОПЗ, сумма, название, номер) с направлением.
- Массовые действия: чекбокс на карточке при наведении, нижняя плашка «Выбрано: N» с назначением ответственного, переносом в этап и снятием выбора. Пока нет Z-18 — последовательные запросы с итоговым тостом «Готово: X, ошибок: Y».
- Кнопки шапки: «Новая заявка», «Из шаблона» (4 встроенных шаблона прототипа + пользовательские Z-14), «Экспорт в Excel» — текущая выборка с учётом поиска, фильтров и выделения, колонки как в `xlList()`.

### 5.6 Лента

Хронология действий в воркспейсе по дням, фильтр по участнику, до 150 записей, клик открывает заявку (прототип: `renderFeed()`). Источник — Z-10.

### 5.7 Отчёты и сверка

- Период отчёта: два календаря и пресеты «Сегодня», «Этот месяц», «Прошлый месяц», «Этот год»; начало не позже конца.
- KPI: количество выдач, сумма БГ, комиссии клиентов, сумма КВ. Распределение сумм по банкам горизонтальными барами. Сворачиваемая детализация всех выдач (колонки `RH` прототипа) с экспортом.
- Сверка КВ: банк, свой период с пресетами «Этот месяц», «Прошлый месяц», «Как в отчёте»; метрики и таблица (клиент, ИНН, закупка/договор, сумма, комиссия, КВ %, сумма КВ) с экспортом.
- В расчёт попадают только гарантии с банком и датой выдачи в периоде. Источник — Z-16; до него — агрегация на клиенте по деталям выданных заявок (параллельно не более 6 запросов).

### 5.8 Банки

- Список `GET /banks` с переключателем «Показать неактивные», добавление, переименование, активация и деактивация (OWNER/ADMIN). Глобальные банки (`is_global`) помечены и не переименовываются.
- По каждому банку — число заявок, где он используется, и поля «Лимит на клиента», «Лимит действует до», «Менеджер / контакт» (Z-05).

### 5.9 Воркспейсы и участники

- Карточки воркспейсов пользователя с ролью; клик переключает воркспейс; создание; переименование и удаление (Z-12, только OWNER).
- Настройки: цвета колонок доски со сбросом к умолчанию (Z-13).
- Участники: имя, email (через `GET /users/{id}`), роль. Смена роли — только OWNER, выбор ADMIN/MEMBER. Удаление — OWNER/ADMIN, OWNER удалить нельзя.
- Роли прототипа (Владелец, Администратор, Менеджер, Участник, Наблюдатель) и чекбоксы прав заменяются ролями API OWNER/ADMIN/MEMBER; под списком — справочная таблица прав из `api.md`.
- Приглашения (OWNER/ADMIN): форма email + роль, список со сроком действия и меткой «истекло», отзыв, «Отправить повторно» (Z-17; до него — отзыв и новое приглашение).

## 6. UI-кит, стили, адаптивность

Визуально результат должен совпадать с прототипом: те же цвета, радиусы, плотность и типографика. CSS прототипа не копируется — значения переносятся в токены Tailwind, а компоненты собираются на Kobalte.

### 6.1 Дизайн-токены

Источник — переменные `:root` в начале `<style>` прототипа. Они объявляются в `@theme` файла `src/styles/app.css` с теми же смысловыми именами:

| Токен прототипа | Назначение | Пример класса Tailwind |
| --- | --- | --- |
| `--bg`, `--sf`, `--sf2` | Фон страницы, поверхности | `bg-bg`, `bg-surface` |
| `--tx`, `--mu` | Основной и приглушённый текст | `text-fg`, `text-muted` |
| `--ln` | Линии и рамки | `border-line` |
| `--ac`, `--ac2`, `--acsoft` | Акцент, hover, мягкий фон акцента | `bg-accent`, `bg-accent-soft` |
| `--ok`/`--okbg`, `--warn`/`--warnbg`, `--danger`/`--dangerbg` | Статусы | `text-ok bg-ok-soft` |
| `--r`, `--shadow` | Радиус 14 px, тень карточек | `rounded-card`, `shadow-card` |

Шрифт: Inter с системным фоллбэком, базовый размер 14 px. Тёмная тема не требуется, но цвета задаются только токенами, чтобы её можно было добавить без правки компонентов.

### 6.2 Компоненты `shared/ui`

Button (primary, default, subtle, danger, icon), Input, MoneyInput, DateInput, DateTimeInput, Select, MultiSelect, Combobox, Textarea, Checkbox, SegmentedControl (`.seg`), Tabs (`.form-tab-switch`), Dialog и ConfirmDialog, Popover и FilterDropdown (`.fdd`/`.fb-pop`), Pill и Badge, Avatar с инициалами, Card, KpiCard, Table с правым выравниванием чисел, EmptyState, Toast, Skeleton, Spinner, FileDrop, BulkBar.

Каждый компонент типизирован, поддерживает `disabled` и состояние ошибки и имеет пример на демо-странице `/dev/ui` (только в dev-сборке).

### 6.3 Адаптивность

Контрольные ширины — брейкпоинты прототипа: 1280, 1100, 1050, 720, 520 px; минимальная ширина 320 px.

- ≥ 1100: сайдбар 258 px, доска в три колонки, отчёты в две колонки.
- 720–1100: сайдбар 228 px, доска с горизонтальным скроллом колонок от 235 px, KPI по два в ряд.
- < 720: сайдбар становится верхней панелью, карточка заявки — полноэкранной, формы в одну колонку, таблицы скроллятся внутри своего контейнера.
- < 520: вкладки формы растягиваются на всю ширину и переносят текст.
- Учитываются safe-area (`viewport-fit=cover`) и `prefers-reduced-motion`.

### 6.4 Доступность

- Все действия доступны с клавиатуры, включая перенос карточек; видимый фокус как в прототипе (`outline 3px` акцентного цвета).
- Диалоги с ловушкой фокуса и возвратом фокуса; вкладки с ролями `tablist`/`tab`; иконки-кнопки с `aria-label`.
- Контраст текста не ниже WCAG AA; цвет не единственный носитель смысла (статусы дублируются текстом).

### 6.5 Состояния

Для каждого списка и экрана есть загрузка (скелетоны), пусто (тексты из прототипа), ошибка (сообщение и «Повторить») и нет прав (сообщение вместо контента).

## 7. Нефункциональные требования и качество

Качество проверяется автоматически в CI: сборка не проходит без зелёных typecheck, lint, unit- и e2e-тестов.

### 7.1 Производительность

- Начальный JS-бандл не более 200 КБ gzip; экраны отчётов, настроек и SheetJS грузятся лениво.
- Доска с 500 заявками: поиск и фильтры отвечают быстрее 100 мс, перетаскивание без рывков. Списки длиннее 100 элементов в колонке — виртуализация или «Показать ещё».
- Lighthouse (desktop) на доске: Performance ≥ 90, Accessibility ≥ 95.

### 7.2 Безопасность

- Никакого `innerHTML` с пользовательскими данными; упоминания и комментарии рендерятся компонентами.
- CSP для продакшен-сервера: `default-src 'self'`, `connect-src` только на API, без `unsafe-inline` для скриптов.
- Токены не логируются; при выходе очищаются все хранилища сессии и кеш запросов.
- Внешние ссылки (ЕИС) открываются с `rel="noopener noreferrer"`; URL проверяется на схему `http(s)`.

### 7.3 Совместимость

Последние 2 версии Chrome, Edge, Firefox, Safari и Яндекс Браузера; iOS Safari 16+, Android Chrome. Интерфейс только на русском, форматы чисел и дат — `ru-RU`.

### 7.4 Тестирование

- Unit (Vitest): маппинг API ↔ форма, расчёт КВ в обоих режимах, проверка ИНН, поиск и фильтры доски, правила переходов статусов, single-flight refresh. Покрытие `domain/` и `api/` не ниже 80 %.
- Компонентные (Testing Library): форма заявки для каждого типа закупки, вкладка «Выдача», фильтр-дропдауны, диалоги архивации.
- E2E (Playwright, MSW или тестовый стенд): регистрация → подтверждение → создание воркспейса; создание заявки 44-ФЗ и НДС; работа с банками и выдача с расчётом КВ; архивация и возврат; отчёт и сверка с экспортом; приглашение участника и вход по нему; истечение access-токена во время работы.
- Визуальная сверка с прототипом: скриншоты ключевых экранов на 1440 и 375 px прикладываются к PR.

### 7.5 Код и процесс

- TypeScript strict, ESLint без предупреждений, Prettier, Conventional Commits.
- CI (GitHub Actions или GitLab CI): `yarn install --immutable`, typecheck, lint, test, build, e2e.
- README: запуск, переменные окружения, генерация типов API, включение заглушек, структура проекта.
- Сборка — статические файлы; пример конфигурации nginx с SPA-фолбэком и CSP прикладывается.

## 8. Этапы, приёмка и заглушки

Работа сдаётся пятью этапами; каждый этап принимается на стенде с реальным бэкендом и демонстрацией сценариев из 7.4, относящихся к этапу.

### 8.1 Этапы

1. **Основа:** репозиторий, стек, CI, генерация типов API, клиент с токенами и обработкой ошибок, UI-кит и токены, каркас с сайдбаром и роутингом.

### 8.4 Открытые вопросы к бэкенду

- Допустимы ли переходы «Выданные → Архив» и «Выданные → В работе» (например, при удалении гарантии)?
- Можно ли передавать `agent_commission_rate` при ручном вводе суммы КВ?
- Можно ли переименовывать глобальные банки (`is_global`) из воркспейса?
- Какие поля реально входят в `ApplicationSummaryResponse` и `status_history[]`?
- Будет ли составной эндпоинт создания заявки с клиентом и закупкой в одной транзакции?
